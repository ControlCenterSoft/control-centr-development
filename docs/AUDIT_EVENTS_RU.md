# Чтение событий аудита Control Center

## Назначение

Control Center хранит административные и security-события в append-only Audit-журнале. API чтения предназначен для уполномоченных администраторов и аудиторов, которым необходимо просматривать фактическую историю событий без изменения самого журнала.

Точка доступа:

`GET /api/v1/audit/events`

## Контроль доступа

Для чтения требуется одновременно:

- действующая аутентифицированная сессия;
- завершённая обязательная смена первоначального пароля после чистой установки;
- глобальное разрешение `audit.events.read`.

Отсутствие разрешения приводит к отказу. API не предоставляет обходного режима или неаутентифицированного экспорта.

## Ограниченное чтение

Ответ выдаётся страницами от новых событий к более старым. По умолчанию возвращается до 50 событий, максимальный размер страницы — 100.

Поддерживаются точные фильтры:

- `action` — действие;
- `outcome` — результат;
- `actor_id` — инициатор;
- `subject_id` — объект/субъект события.

В development-границе 0.33 дополнительно подготовлен bounded metadata search через `search`. Он выполняет регистронезависимый поиск подстроки только по безопасному набору метаданных: event ID, action, outcome, actor ID, subject ID, source IP и correlation ID. Structured `details` намеренно не участвуют в поиске, даже если уже прошли redaction.

Поиск разрешён только при одновременной передаче `from` и `to` в RFC3339. Окно должно быть положительным и не превышать 31 день; поисковая строка содержит от 3 до 128 Unicode-символов. Это ограничивает стоимость запроса и уменьшает риск превращения Audit API в механизм массового discovery чувствительных данных.

Временные границы `from`/`to` также могут использоваться без `search` вместе с точными фильтрами. Нижняя и верхняя границы включаются в выборку.

Произвольный SQL, регулярные выражения, поиск по structured details, полнотекстовые условия и неограниченная выгрузка этим API не поддерживаются.

## Пагинация

Если доступны более старые события, ответ содержит `next_cursor`. Значение cursor является непрозрачным для клиента: его необходимо передать без изменения в следующем запросе как параметр `cursor`.

Клиент не должен строить cursor самостоятельно или полагаться на его внутренний формат. Некорректный, неизвестный или неоднозначный cursor отклоняется.

## Защита данных

Audit-журнал не предназначен для хранения значений паролей, session tokens, cookies, API keys, private keys или других credentials. Structured details проходят redaction при записи, а чтение повторно применяет безопасное представление данных.

Metadata search не просматривает `details` и не сохраняет исходную поисковую строку в Audit evidence. В evidence фиксируется только факт применения поиска и использованные временные границы.

Ответ помечается `Cache-Control: no-store`.

## Проверяемость чтения

Успешное чтение само формирует Audit-событие `audit.events_list` с результатом `success`. В evidence фиксируются параметры ограниченного запроса и число возвращённых событий. При metadata search фиксируется `search_applied=true`, но не само значение `search`.

Если журнал можно прочитать, но evidence успешного чтения записать невозможно, Control Center возвращает ошибку и не отдаёт прочитанные события клиенту. Это сохраняет правило: привилегированное чтение Audit не должно происходить без собственной аудируемой записи.

Ошибка чтения журнала возвращается как временная недоступность и не преобразуется в пустую успешную страницу.

## Целостность

Чтение не изменяет существующие Audit-события и не ослабляет append-only свойства хранилища. Каждое загружаемое PostgreSQL-событие проверяется по сохранённому hash перед выдачей; ошибка декодирования или проверки приводит к fail-closed отказу запроса.

Полная проверка непрерывности hash-chain выполняется отдельной read-only операцией `GET /api/v1/audit/integrity`. Она возвращает только агрегированное подтверждение целостности и не заменяет обычное постраничное чтение событий. Подробности описаны в `docs/AUDIT_INTEGRITY_RU.md`.

## Пример последовательности

1. Запросить первую страницу с нужным точным фильтром и ограничением.
2. Для metadata search выбрать явный короткий временной диапазон и передать `search`, `from`, `to`.
3. Обработать события в порядке от новых к старым.
4. Если присутствует `next_cursor`, передать его без изменения в следующем запросе как параметр `cursor` вместе с теми же фильтрами и временными границами.
5. Завершить чтение, когда `next_cursor` отсутствует.

Контракт API описан в `api/openapi-audit-events.yaml`.
